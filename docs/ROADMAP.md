# 1. المقدمة

## 1.1 الغرض

تحوّل هذه الوثيقة نطاق المنتج المحدد في `docs/SRS.md` إلى **برنامج تنفيذ زمني مرحلي**: مراحل كبرى، إصدارات (Releases)، معالم خروج قابلة للقياس، فرق ومسؤوليات، مؤشرات نجاح، وسجل مخاطر على الطريق. وهي أداة الحوكمة التي:

- يقيس عليها **صاحب المنتج** تقدّم المشروع ويتخذ عندها قرارات الاعتماد والتوسع.
- يلتزم بها **الفريق الهندسي** لضمان البناء التدريجي الآمن وفق Master PLAN §128/§129.
- تُشتق منها **خطة QA** (معالم القبول AC لكل مرحلة) ومراجعات **الامتثال والمخاطر** (بوابات الأمان قبل كل توسع).

## 1.2 فلسفة النسخة الأولى: "MVP هنا لا يعني تطبيقاً ناقصاً"

القاعدة الحاكمة (Master PLAN §138): النسخة الأولى المقبولة يجب أن تحتوي على:

> Authentication — Region Eligibility — Wallet — Balance — Ledger — Transfer — Deposit — Withdrawal — Fees — Limits — Transactions — Receipts — Notifications — Support — WhatsApp — Admin — Audit — Reports — System Controls

ثم تُضاف الخدمات الاختيارية فوق هذا الأساس.

**الترجمة العملية في هذه الخارطة:**

- المرحلة 1 (MVP الأساس المالي) تشمل **الإدارة الأساسية (Admin الأساسيات + Audit + Reports)** صراحةً — لأن §138 يعتبرها جزءاً من "النسخة الأولى الحقيقية"، ولأن Master §129 يضع Admin وReports في ذيل ترتيب العمل داخل كل Phase (لا تُبنى الوظيفة بمعزل عن تحكمها الإداري — R-09).
- الاستثناءات الوحيدة عن هذه الفلسفة هي ما أُجّل صراحة في SRS ملحق ج: FR-CRY (Won't — قرار مستقل)، FR-TRF-007 (Won't — Standing Orders)، وبنود Launch (FR-KYC-010/011، FR-ACC-005، FR-OFF-004، FR-ADM-007).

## 1.3 قاعدة البناء التدريجي الآمن (Master PLAN §151)

تسري على طول هذه الخارطة البنود التنفيذية الحاكمة:

1. **نفّذ كل مرحلة تدريجياً**، وشغّل الاختبارات الفعلية بعد كل مرحلة (لا انتقال مع خلل جوهري).
2. **كل حالة تعمل**: كل شاشة مالية تُسلَّم بحالاتها الإلزامية كاملة (SRS §7.3: Initial/Loading/Success/Empty/Error/Pending/Unauthorized/Offline/Maintenance/Restricted/OutOfServiceArea/ForceUpdate) — يُمنع تصميم حالة النجاح فقط.
3. **كل Commit يمثل حالة تعمل**؛ وإذا فشلت محاولتان متتاليتان في إصلاح نفس المشكلة نعود إلى آخر حالة مستقرة (Master §151 البندان 14–15).
4. **أي أمر غير مغطى** — معماري أو مالي أو أمني — يُوقف التنفيذ عنده ويُطلب قرار صاحب المنتج قبل تغييره (Master §151 البند 13).
5. **قواعد الإنتاج (Master §140)** نافذة من أول يوم على بيئة Production: يمنع Fake money وMock provider وTest account وHardcoded balance/admin/fee/region list وFake success state — بيانات الاختبار حصراً في Staging (C-10).

## 1.4 اصطلاحات التوقيت

- تُكتب المدد بصيغة **"الشهر 1–3"** و**"الأسبوع 1–2"** فقط؛ الشهر 1 يبدأ من نقطة انطلاق التنفيذ (بعد اعتماد هذه الوثيقة وتجهيز الفريق §11).
- **كل المدد تقديرية تخطيطية** قابلة للتعديل بعد اعتماد الفريق التقني — ولا تمثل مواعيد نهائية ملزمة.
- التداخل الزمني بين مرحلتين مقصود (انتقال سلس) وكل تداخل موضح في مكانه.
- ترتيب الأولوية عند أي تعارض: Master PLAN.md ← SRS.md ← هذه الوثيقة.

**الترتيب داخل كل Phase حرفياً وفق Master §129** (لا تُبنى الشاشات ثم يبحث عن Backend):

```
Understand Rule ← Design Data ← Design State Machine ← Backend ← Security/Permission

```

> ملاحظة ربط: معرفات الشاشات النهائية SC- (المقترحة في وثيقة الشاشات المكتوبة بالتوازي: docs/SCREENS_FLOWS.md) ستُربط بجدول التتبع (§10) عند اعتمادها؛ الإحالات هنا لمجموعات SRS §7.2 (م1..م14) لأنها هي المرجع المستقر.

```
Create Account ← Become Eligible ← Receive Deposit ← See Balance ← Send Money
← Receiver Gets Money ← Fee Recorded ← Both Get Notifications ← Both See Statement
← Receipt Exists ← Admin Sees Transaction ← Ledger Matches ← Report Includes It
← Audit Trail Exists
```

|---|---|---|---|

## 6.5 خطة Rollback المرجعية (Master §137)

```
مشكلة في إصدار جديد
   ↓
Disable affected feature (تعطيل الميزة المتأثرة — Feature Flags: FR-ADM-038)
   ↓
Force-safe state (فرض حالة آمنة — حالات النظام: FR-ADM-041)
   ↓
Backend rollback if applicable (Rollback خادمي حيث ينطبق — Migrations مُصدّرة: Master §134)
   ↓
Release corrective version (إصدار تصحيحي — FR-ADM-040)
```

> لا يتم التلاعب بالمعاملات المكتملة بسبب مشكلة UI (R-04) — التصحيح المالي بـ Reversal/Adjustment موثّق فقط (FR-LDG-007).

| 3 | الشهر 9 | حضرموت + المهرة + سقطرى | استقرار الخطوة 2 + خطة دعم ميداني لكل محافظة |

```
الخطوة 1 (الشهر 7):  عدن (توسيع) + لحج + أبين
        ↓ شرط: قرار إقليمي D-05 + جاهزية وكلاء وFloat (RK-05) + طاقة طابور KYC
الخطوة 2 (الشهر 8):  شبوة + الضالع
        ↓ شرط: استقرار أسبوعين بلا حادث جوهري
الخطوة 3 (الشهر 9):  حضرموت + المهرة + سقطرى ← اكتمال المحافظات الثماني (SRS §3.1)
        ↓ شرط: استقرار + خطة دعم ميداني لكل محافظة (A-05)
```

# 15. حوكمة التقدم

قواعد Master §151 مطبقةً على إدارة الخارطة نفسها:

1. **Definition of Done لكل بند (Master §127):** لا يُعدّ البند مكتملًا دون UI + Backend + Database + Authorization + Validation + Error/Loading/Success States + Audit + Notifications + Reports + Admin Control + Testing — وللبنود المالية إلزامياً: Ledger + Atomicity + Idempotency + Reconciliation.
2. **لا انتقال لمرحلة تالية مع خلل جوهري** (§151 البند 11): الخلل الجوهري = فشل AC، فروق Ledger، ثغرة حرجة، حالة غامضة بلا تعريف (NFR-REL-004). يُوثَّق ويُعالج قبل بوابة الخروج أو يُتخذ قرار صاحب المنتج بتأجيل موثق.
3. **كل حالة تعمل:** كل شاشة مالية بكل حالات SRS §7.3، وكل معاملة بحالات آلة حالتها (SRS ملحق أ) — لا وظيفة «معلقة» تنتظر نصفها الآخر (Master §152).
4. **كل Commit حالة تعمل**؛ وفشل محاولتي إصلاح متتاليتين ← العودة لآخر حالة مستقرة (§151 البندان 14–15).
5. **إيقاف وطلب قرار عند أي أمر غير مغطى** (§151 البند 13): عبر سجل القرارات (§3.3 وملحقات البوابات) — ولا يغيّر الفريق تصميم Master PLAN أو قواعده الجوهرية من تلقاء نفسه.
6. **إيقاع التقرير:** تقرير أسبوعي من مدير المشروع (حالة المعالم، مخاطر §14، قرارات معلقة) + مراجعة بوابة رسمية عند كل M-0..M-8 بحضور صاحب المنتج.
7. **قواعد الإنتاج (Master §140) رقيب دائم:** لا fake money ولا mock ولا حسابات اختبار في Production — بوابات Internal Alpha (§4.7) تشترط قراراً موثقاً في نمط التشغيل.

**تعريف الخلل الجوهري ومسار التصعيد:**

| التصنيف | أمثلة (مرجعية) | الإجراء |
|---|---|---|
| مالي | فروق Ledger، فشل AC مالي، خصم غير مفسَّر (FR-BIL-004) | إيقاف الميزة + Reversal/Adjustment موثق + تصعيد فوري لصاحب المنتج |
| أمني | ثغرة حرجة، اختراق حساب إداري (Master §124) | إيقاف النشر + مراجعة أمنية + إبلاغ موثق |
