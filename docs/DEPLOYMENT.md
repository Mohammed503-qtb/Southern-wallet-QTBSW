# 0. نظرة عامة والمخطط المعماري

## 0.1 الغرض

هذا دليل تشغيلي (Runbook) كامل لمهندس نشر يقرأ العربية: من خادم فارغ إلى خدمة **محفظة الجنوب** تعمل على نطاق إنتاجي بشهادة HTTPS تلقائية، مع نسخ احتياطي مُختبَر ومراقبة وخطة تراجع. كل الأوامر هنا قابلة للنسخ والتنفيذ كما هي، ومسارات الملفات تطابق مستودع المشروع حرفياً.

## 0.2 المخطط المعماري (نشر الخادم الواحد)

## 0.3 مكونات حزمة النشر (الملفات المسلَّمة في هذه الحزمة)

| الملف | الدور |
|---|---|
| `Dockerfile` | بناء الصورة متعدد المراحل (builder → runner) على `oven/bun:1` |
| `docker-compose.yml` | خدمتا `app` و`caddy` + الشبكة الداخلية + volume `app-db` |
| `deploy/docker-entrypoint.sh` | إنشاء مخطط قاعدة البيانات عند أول تشغيل ثم تشغيل الخادم |
| `deploy/Caddyfile` | إعداد بوابة الإنتاج: HTTPS تلقائي + ضغط + وكيل عكسي (النطاق عبر `{$SW_DOMAIN}`) |
| `deploy/backup.sh` | نسخة احتياطية آمنة متسقة + دوران (7 يوميات + 4 أسبوعيات) |
| `deploy/restore.sh` | استرجاع فعلي مع تحقق وتراجع تلقائي + وضع اختبار `--drill` |
| `.dockerignore` | سياق بناء نظيف — لا تسريب لقاعدة التطوير أو السجلات أو `.env` |
| `.github/workflows/ci.yml` | بوابة جودة GitHub Actions لكل push/PR إلى main (lint + build) |
| `.env.production.example` | نموذج بيئة الإنتاج (آمن للالتزام — قيم placeholder فقط) |
| `docs/DEPLOYMENT.md` | هذه الوثيقة |

## 0.4 قرارات معمارية مفاتيحية (مثبتة بالتجربة)

1. **صورة واحدة متعددة المراحل**: مرحلة builder تثبّت وتولّد وتبني؛ مرحلة runner نظيفة تعمل بمستخدم غير جذري (`bun`) ولا تحوي قاعدة بيانات — البيانات كلها في وحدة التخزين `app-db`.
2. **إنشاء المخطط عند أول تشغيل** (وليس أثناء البناء): `deploy/docker-entrypoint.sh` يفحص وجود ملف القاعدة في `/app/db`، فإن غاب نفّذ `bunx prisma db push --accept-data-loss` — بذلك تعمل الصورة على أي خادم بلا خبز بيانات فيها، ويُحفظ مسار Migrations الموحّد (Master §134: db push كأداة المخطط في SQLite لهذه المرحلة).
3. **شجرة أدوات Prisma مغلقة داخل الصورة** (35 حزمة: CLI + العميل + المحركات + تبعياتها): يجعل `bunx prisma db push` يعمل داخل الحاوية **دون اتصال بالشبكة** ودون تثبيت كامل التبعيات — مُتحقَّق منه محلياً قبل كتابة Dockerfile (انظر §8 إن غيّرت إصدار Prisma).
4. **Caddy بوابةً وحيدة**: التطبيق لا يُنشر على منافذ المضيف إطلاقاً (`expose` داخلي فقط)؛ TLS تلقائي من Let's Encrypt بلا أي إعداد شهادات يدوي، وHTTP يُحوَّل دائماً إلى HTTPS.
5. **النسخ الاحتياطي عبر `sqlite3 .backup`**: نسخة متسقة (online backup) حتى والقاعدة نشطة — لا إيقاف خدمة لأجل النسخ اليومي؛ الاسترجاع وحده نافذة صيانة معلنة.
6. **`/api/health` متاح خارجياً عن قصد** عبر Caddy لمراقبة الجهات الخارجية (Uptime Kuma) — يعيد 200 مع `{db:true}` أو 503 عند تعذر القاعدة.

## 1.1 الخادم (موصى به للـ Closed Beta)

| البند | الحد الأدنى | الموصى به |

> الذاكرة المهمة أثناء **بناء الصورة** (رام Docker ≥ 2GB متاح) — التشغيل اليومي أخف بكثير.

## 1.2 البرمجيات على الخادم

| البرنامج | الإصدار | التحقق |
|---|---|---|

| git | أي إصدار حديث | `git --version` |

## 1.3 النطاق وDNS

- نطاق مملوك (مثال: `wallet.example.com`) مع **سجل A** يشير إلى IP الخادم العام.
- (اختياري للتحقق) سجل **TXT** وفق ما تطلبه Let's Encrypt عند استخدام DNS challenge — الوضع الافتراضي هنا HTTP-01 عبر المنفذ 80 فلا حاجة إليه.
- لا تستضف النطاق على CDN تمنع تحدي ACME أو تغيّر IP الظاهر إلا مع ضبط `trusted_proxies` لاحقاً.

## 1.4 مفاتيح الوصول

- صلاحيات SSH بمفتاح (كلمة مرور SSH معطلة — انظر §7.2).
- صلاحية sudo لتنفيذ أوامر Docker (أو عضوية مجموعة `docker`).

# 2. خطوات النشر الأولى (خطوة بخطوة)

> نفّذ الأوامر بترتيبها. المتغير الوحيد الذي **يجب** تعديله هو `SW_DOMAIN`.

## 2.1 جلب المستودع

```bash
sudo mkdir -p /opt && cd /opt
sudo git clone https://github.com/Mohammed503-qtb/Southern-wallet-QTBSW.git south-wallet
cd /opt/south-wallet
# للملكية إن كنت ستعمل بمستخدم نشر مخصص:
# sudo chown -R deploy:deploy /opt/south-wallet
```

## 2.2 تهيئة بيئة الإنتاج

```bash
cp .env.production.example .env.production
nano .env.production        # أو vim
```

عدّل القيم التالية (التعليمات الكاملة داخل الملف نفسه — عربي/إنجليزي):

| المتغير | القيمة | ملاحظة |
|---|---|---|
| `SW_DOMAIN` | نطاقك الحقيقي مثل `wallet.example.com` | **إلزامي** — يقرؤه Caddy لإصدار الشهادة |
| `SW_ACME_EMAIL` | بريد المسؤول | موصى به — تنبيهات انتهاء/فشل الشهادة |
| `DATABASE_URL` | `file:/app/db/custom.db` | لا تغيّره — مسار ثابت داخل وحدة التخزين، **وبلا علامات اقتباس** |
| `HOSTNAME` | `0.0.0.0` | لا تغيّره — مطلوب لخادم standalone داخل الحاوية |
| `PORT` / `NODE_ENV` | `3000` / `production` | لا تغيّرهما |

> ⚠️ **أمان**: `.env.production` خارج التتبع في git (النمط `.env*` في `.gitignore`). لا ترفعه أبداً ولا تلصق محتواه في أي مكان.

## 2.3 التشغيل الأول (بناء + إقلاع)

```bash
docker compose up -d --build
```

ما يحدث تلقائياً عند أول تشغيل (بلا أي خطوة إضافية):

1. تُبنى صورة `south-wallet/app:latest` من `Dockerfile` (بضع دقائق).
2. تُنشأ وحدة التخزين `app-db` فارغة وتركّب على `/app/db`.
3. `docker-entrypoint.sh` يجد القاعدة غائبة → ينشئ المخطط كاملاً عبر `prisma db push` (سجّل الرسالة: `تم إنشاء مخطط قاعدة البيانات بنجاح`).
4. يقلع الخادم على 3000 داخل الشبكة الداخلية `sw-net`.
5. ينتظر Caddy حتى **صحة** التطبيق (`depends_on: service_healthy`) ثم يقلع على 80/443.
6. عند أول وصول إلى `https://<النطاق>` تُصدر شهادة Let's Encrypt تلقائياً (قد يستغرق أول طلب ثوانٍ إضافية).

## 2.4 التحقق من النشر

```bash
# 1) حالة الحاويتين (يجب أن تصبح healthy)
docker compose ps

# 2) فحص الصحة داخلياً (يتوقع {"db":true,...})
docker compose exec app curl -s http://127.0.0.1:3000/api/health

# 3) فحص الصحة خارجياً عبر HTTPS (من جهازك)
curl -s https://wallet.example.com/api/health

# 4) سجلات التشغيل (ابحث عن رسائل [docker-entrypoint])
docker compose logs -f app
```

معايير النجاح:

| الفحص | النتيجة المتوقعة |
|---|---|
| `docker compose ps` | `app` = `healthy` و`caddy` = `running` |
| `curl /api/health` | HTTP 200 و`"db":true` |
| فتح `https://<النطاق>` في المتصفح | شاشة الدخول (PWA عربي RTL) مع قفل TLS |
| `docker compose logs caddy` | لا أخطاء شهادة (certificate obtained successfully) |

## 2.5 ملاحظات على HTTPS التلقائي

- الشهادة تُخزَّن في volume `caddy_data` — **لا تنفّذ `docker compose down -v` أبداً** (تحذف القاعدة والشهادات معاً).
- التجديد تلقائي قبل الانتهاء (~30 يوماً)؛ حد المعدل عند الحذف المتكرر للـvolume: 5 إصدارات/أسبوع لنفس النطاق — راجع بريد `SW_ACME_EMAIL`.
- للتحقق اليدوي: `docker compose logs caddy | grep -i certificate`.

# 3. تهيئة البيانات (المخطط والبذور)

## 3.1 أول تشغيل: المخطط تلقائي

كما في §2.3 — لا خطوة يدوية إطلاقاً: المخطط يُنشأ في وحدة التخزين عند أول إقلاع عبر `prisma db push`، وكل إعادة تشغيل لاحقة تتخطى الإنشاء (الرسالة: `ملف قاعدة البيانات موجود — تخطي إنشاء المخطط`).

عند تحديث `prisma/schema.prisma` في إصدار جديد، طوّر المخطط يدوياً بأمر واحد (انظر §5.2):

```bash
docker compose exec app bunx prisma db push --accept-data-loss --schema /app/prisma/schema.prisma --skip-generate
```

> ⚠️ `--accept-data-loss` تسمح بحذف أعمدة/جداول لم تعد في المخطط — **خذ نسخة احتياطية قبلها دائماً** (§4.1). توثيق Migrations الموحّد في Master §134.

## 3.2 البذور الافتراضية (اختيارية — للتجربة فقط)

المستودع يحوي ثلاثة ملفات بذور idempotent داخل `prisma/`:

| الملف | المحتوى |
|---|---|
| `prisma/seed.ts` | المرحلة 1: مستخدمو الأدوار + محافظ العملات الثلاث + قواعد الرسوم/الحدود + المحافظات + سجل تاريخي متوازن + أرصدة الوكلاء (Float) |
| `prisma/seed-phase2-payments.ts` | رسوم BILLS/TOPUP/CARDS + معاملات تاريخية للخدمات + تفعيل `ServiceState` للثلاث |
| `prisma/seed-phase2-merchant.ts` | تاجران تجريبيان + قاعدة رسوم MERCHANT_PAY + حوالتان واردتان + تفعيل الخدمتين |

التشغيل (الصورة الإنتاجية تحوي `src/` و`prisma/` كاملة تحديداً لهذا):

```bash
# المرحلة 1 أولاً (تلزمها البذور اللاحقة)
docker compose exec app bun prisma/seed.ts
# ثم مرحلة 2 (كل واحد مستقل وidempotent)
docker compose exec app bun prisma/seed-phase2-payments.ts
docker compose exec app bun prisma/seed-phase2-merchant.ts
```

حسابات الدخول التجريبية بعد البذور (PIN الافتراضي `123456`):

| الدور | الهاتف |
|---|---|
| عميل موثّق (KYC كامل) | 770000001 |
| عميلة (غير موثّقة جزئياً) | 770000002 |
| خارج النطاق الجغرافي (AC-07) | 770000003 |
| تاجر (نقطة البيع QR) | 770000020 |
| وكيل نقدي | 770000010 |
| مدير / امتثال / دعم | 770100001 / 770100002 / 770100003 |

## 3.3 ⚠️ تحذير إلزامي: بيانات البذور للتجربة فقط

- البذور **تمسح الجداول وتعيد زرع بيانات تجريبية** (idempotent لكنها مدمّرة لما قبلها) — لا تشغّلها على قاعدة تحوي عملاء حقيقيين أبداً.
- للنشر **العام**: أطلق بقاعدة نظيفة (المخطط فقط — تلقائي) ثم أنشئ حسابات فعلية عبر مسارات التسجيل والKYC، وفعّل الخدمات من لوحة الإدارة (ServiceState) عند الجاهزية التشغيلية لكل خدمة (قاعدة §140: الإدارة لا تتجاوز النظام).
- مزودو الدفع/الفواتير في هذه المرحلة **محاكاة حتمية** (مستحق الفاتورة مشتق دالة من رقم الحساب) — انظر §10 قبل أي عرض على جمهور خارج فريق الاختبار.

# 4. النسخ الاحتياطي والاسترجاع

> البوابة الحاكمة: **NFR-REL-002** — «نسخة احتياطية غير مُختبرة = نسخة غير موجودة». هذا القسم يفيها بأدوات آلية (backup/restore) وبإجراء اختبار دوري موثق.

## 4.1 تفعيل النسخ اليومي (كرون)

```bash
# مجلد النسخ خارج المستودع (أفضل ممارسة — قرص/قسم مستقل إن أمكن)
sudo mkdir -p /var/backups/south-wallet
sudo chown "$USER" /var/backups/south-wallet

# جدولة يومية 02:00 (كرون المستخدم الحالي)
crontab -e
# أضف السطر (سطر واحد):
# 0 2 * * * cd /opt/south-wallet && BACKUP_DIR=/var/backups/south-wallet bash deploy/backup.sh >> /var/log/sw-backup.log 2>&1
```

ما يفعله `deploy/backup.sh` في كل تشغيل:

1. فحص سلامة قاعدة المصدر (`PRAGMA integrity_check`) — لا نسخ لقاعدة تالفة.
2. نسخة **متسقة** عبر `sqlite3 .backup` داخل الحاوية (يعمل والقاعدة نشطة — بلا توقف خدمة).
3. تحقق من الناتج + كتابة بصمة `sha256` جانبية.
4. دوران تلقائي: **7 نسخ يومية + 4 نسخ أسبوعية** (الترقية للأسبوعية كل سبت أو عند غياب أسبوعي).
5. سجل كامل في `/var/backups/south-wallet/backup.log`.

التحقق اليدوي بعد التفعيل:

```bash
bash deploy/backup.sh                      # تشغيل يدوي فوري
ls -lh /var/backups/south-wallet/daily/    # الملفات sw-db-YYYYMMDD-HHMMSS.db
tail -20 /var/backups/south-wallet/backup.log
```

## 4.2 الاسترجاع الفعلي (نافذة صيانة)

الاسترجاع **يوقف الخدمة مؤقتاً** (دقائق معدودة) — أعلِن نافذة صيانة قبلها:

```bash
cd /opt/south-wallet
bash deploy/restore.sh /var/backups/south-wallet/daily/sw-db-YYYYMMDD-HHMMSS.db
```

خطوات السكربت (وضع docker compose): تحقق (وجود + sha256 + سلامة) ← **لقطة أمان** للقاعدة الحالية (`pre-restore-<طابع>.db`) ← إيقاف app ← وضع النسخة محل القاعدة وتنظيف ملفات WAL القديمة ← إعادة التشغيل ← فحص `/api/health` حتى 60 ثانية ← **إن فشل: تراجع تلقائي** إلى لقطة الأمان. بعد النجاح تحقق يدوياً: (1) تسجيل دخول مستخدم معروف، (2) لوحة الإدارة → فحص الدفاتر (Σ=0). لا تحذف لقطة الأمان قبل 48 ساعة.

## 4.3 اختبار الاسترجاع الدوري (--drill) — بوابة NFR-REL-002

شغّل شهرياً (أو بعد كل تغيير جوهري في البنية) على أحدث نسخة:

```bash
bash deploy/restore.sh --drill /var/backups/south-wallet/daily/sw-db-YYYYMMDD-HHMMSS.db
```

الوضع يتحقق من السلامة ويعرض أعداد صفوف الجداول المالية (User/Wallet/Transaction/LedgerEntry) **دون أي مساس بقاعدة الإنتاج** — ثم أرشف النتيجة.

### 4.4 أهداف RPO / RTO

| المؤشر | الهدف في هذه الحزمة | الأساس |
|---|---|---|
| RPO (أقصى فقد بيانات) | ≤ 24 ساعة (الكرون اليومي) | لاحقاً: تكرار النسخ كل 6 ساعات إن لزم |
| RTO (زمن العودة للخدمة) | ≤ 30 دقيقة (استرجاع مُختبر) | يقيسه restore.sh فعلياً في كل استرجاع — سجّل الرقم |

# 5. التحديثات والإصدارات

## 5.1 تحديث إصدار (روتين قياسي)

```bash
cd /opt/south-wallet
bash deploy/backup.sh                                   # 1) نسخة احتياطية قبل أي تحديث
git pull origin main                                    # 2) جلب الإصدار الجديد
docker compose build app                                # 3) بناء الصورة الجديدة
docker compose up -d app                                # 4) استبدال الحاوية (نفس وحدة التخزين)
docker compose ps && curl -s https://<النطاق>/api/health  # 5) تحقق
```

- التحديث لا يمس وحدة التخزين `app-db` — البيانات باقية عبر الاستبدال.
- إن شمل الإصدار تغيير مخطط: نفّذ أمر §3.1 بعد البناء وقبل التحقق (وبعد نسخة احتياطية).
- **صفر توقف تقريبي مع Caddy**: أثناء `up -d app` تستبدل Compose الحاوية خلال ثوانٍ؛ يظهر 502 لثوانٍ معدودة فقط (للترقية بلا توقف إطلاقاً مستقبلاً: نسق blue/green بجهازين — خارج نطاق هذه الحزمة، انظر §10).

## 5.2 خطة التراجع (Rollback — مبسطة من Master §137)

القاعدة المرتبة: **تعطيل الميزة ← حالة آمنة ← rollback**، بهذا الترتيب حرفياً:

1. **تعطيل الميزة دون تراجع كامل إن أمكن**: كل خدمة مالية لها مفتاح `ServiceState` يديره المدير من لوحة الإدارة — عطّل الخدمة المشكلة أولاً (الحالة الآمنة: المحفظة تظل تعرض الأرصدة والسجل وتستقبل الاستعلام فقط دون العمليات المعطلة).
2. **إن استمر الخلل (بنية/بيانات)**: تراجع الإصدار:

   ```bash
   docker compose stop app
   git checkout <وسم-الإصدار-السابق>          # مثال: git checkout v1.0
   docker compose build app && docker compose up -d app
   ```

3. **إن أفسد تحديثٌ البيانات**: استرجع آخر نسخة احتياطية سليمة (§4.2) ثم أعد التحقق من توازن الدفاتر (لوحة الإدارة → فحص الدفاتر).
4. وثّق كل تراجع في worklog مع السبب والإجراء — لا تراجع صامت.

# 6. المراقبة

## 6.1 فحص الجاهزية المدمج

`GET /api/health` (متاح خارجياً عبر Caddy **عن قصد** لأدوات المراقبة):

```json
{ "ok": true, "data": { "db": true, "time": "2026-09-12T00:00:00.000Z" } }
```

- `db:true` = اتصال قاعدة البيانات سليم (`SELECT 1`)؛ HTTP 503 عند التعذر.
- أيضاً: `docker compose ps` (حالة healthcheck كل 30 ثانية) و`HEALTHCHECK` داخل الصورة.

## 6.2 الأدوات المقترحة (خارج هذه الحزمة)

| الأداة | الغرض | ملاحظات |
|---|---|---|
| Uptime Kuma | مراقبة توفر خارجية (HTTP 200 على `/api/health` كل 60 ثانية + تنبيه Telegram/بريد) | self-hosted — حاوية Compose مستقلة على نفس الخادم أو خادم ثانٍ |
| Sentry | تتبع أخطاء التطبيق من المتصفح والخادم | يتطلب DSN — أضفه لاحقاً ضمن مرحلة hardening |
| docker stats / ctop | استهلاك CPU/RAM للحاويات | فوري بلا تثبيت |

## 6.3 مؤشرات NFR المطلوب مراقبتها (من SRS §6.1)

| المؤشر | الهدف | طريقة القياس الأولية |
|---|---|---|
| زمن الاستجابة p95 لواجهات المال | ≤ 2 ثانية | Uptime Kuma (زمن الاستجابة) + أدوات load خفيفة |
| التوفر الشهري | ≥ 99.5% | سجل Uptime Kuma (≈ ≤ 3.6 ساعة انقطاع/شهر) |
| توازن الدفاتر Σ=0 | دائماً | فحص دوري أسبوعي: لوحة الإدارة → فحص الدفاتر (ledger-check) |

> سجّل قراءة أسبوعية لهذه المؤشرات في جدول داخلي حتى الانتقال لأدوات لوحات (Grafana) لاحقاً.

# 7. الأمان التشغيلي

## 7.1 جدار ناري (ufw مثال)

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH            # أو منفذ SSH المخصص
sudo ufw allow 80/tcp             # HTTP → تحويل + تحديات ACME
sudo ufw allow 443/tcp            # HTTPS
sudo ufw allow 443/udp            # HTTP/3 (اختياري)
sudo ufw enable
sudo ufw status verbose
```

> لا تفتح 3000 أبداً — التطبيق داخل الشبكة الداخلية `sw-net` خلف Caddy فقط.

## 7.2 وصول SSH بمفاتيح

```bash
# على الخادم: أضف مفتاحك ثم عطّل كلمة مرور SSH
sudo nano /etc/ssh/sshd_config
#   PasswordAuthentication no
#   PermitRootLogin no
sudo systemctl reload ssh
```

## 7.3 تحديثات النظام

```bash
sudo apt update && sudo apt upgrade -y      # شهرياً على الأقل + عند CVEs حرجة
docker system prune -f                      # تنظيف صور/طبقات معلقة (لا يمس volumes)
```

## 7.4 إدارة الأسرار — قاعدة صارمة

- **لا أسرار في المستودع أبداً**: `.env*` مستثنى من git؛ `.env.production` يعيش على الخادم فقط بملكية مستخدم النشر وصلاحية `600`:
  ```bash
  chmod 600 /opt/south-wallet/.env.production
  ```
- النموذج `.env.production.example` آمن للالتزام (قيم placeholder فقط) — إن رفض git تتبعه بسبب النمط `.env*` فالتزمه صراحة: `git add -f .env.production.example`.
- شهادة TLS وأكوادها: داخل `caddy_data` (لا نسخها ولا إخراجها من الخادم).
- عند ظهور مفاتيح مزودين حقيقيين لاحقاً (SMS/KYC): نفس النمط — متغيرات في `.env.production` على الخادم فقط، لا في الكود ولا المستودع.

## 7.5 قيود الوصول للوحة الإدارة (لاحقاً — موثقة كالتزام)

لوحة الإدارة (`/console` — أدوار ADMIN/COMPLIANCE/SUPPORT/AGENT) متاحة حالياً عبر نفس النطاق بعد المصادقة. للإنتاج العام (البوابة M-7 وما بعدها) التزم الحد الأدنى التالي:

- قصر الوصول على قائمة IP مكتب العمليات (عبر `ufw` أو قاعدة Caddy `@blocked not remote_ip ...`).
- تفعيل MFA الإداري ومراجعة سجل التدقيق (AuditLog) أسبوعياً — مواصفات التفصيل في docs/PRODUCTION_READINESS.md.

# 8. استكشاف الأخطاء

## 8.1 أوامر التشخيص الأولى

```bash
docker compose ps                          # حالة الحاويات وصحتها
docker compose logs -f app                 # سجلات التطبيق (رسائل [docker-entrypoint] عند الإقلاع)
docker compose logs -f caddy               # سجلات البوابة (الشهادات/الأخطاء 502)
docker compose exec app curl -s http://127.0.0.1:3000/api/health   # صحة داخلية
docker compose exec app ls -lh /app/db     # ملف القاعدة وحجمه
docker compose exec app sqlite3 /app/db/custom.db 'PRAGMA integrity_check;'
docker compose logs app | grep -i error | tail -50
```

## 8.2 مشاكل شائعة وحلولها

| العرض | السبب الأرجح | الحل |
|---|---|---|
| الشهادة لا تُصدر (`logs caddy`: timeout/acme error) | سجل DNS لا يشير للخادم أو المنفذ 80 مغلق أو جدار ناري | تحقق `dig <النطاق>` من الخارج؛ `curl http://<النطاق>` يجب أن يعيد تحويلاً؛ افتح 80/443 في ufw وcdn/الراوتر |
| `app` يعلق على `starting` ثم `unhealthy` | مسار القاعدة/أذونات وحدة التخزين | `docker compose logs app` — غالباً رسالة entrypoint عن `DATABASE_URL`؛ تحقق أن `.env.production` يحوي `DATABASE_URL=file:/app/db/custom.db` بلا اقتباس، وأن `app-db` لم يُنشأ بملكية root (§8.3) |
| 502 من Caddy بعد إقلاع صحي | التطبيق لم يكتمل بعد (start_period) | انتظر 30 ثانية ثم أعد الفحص؛ إن استمر راجع سجلات app |
| رسالة entrypoint: `DATABASE_URL غير مضبوط` | `.env.production` غائب أو خارج مسار compose | `cp .env.production.example .env.production` في جذر المستودع ثم `docker compose up -d` |
| الخادم يربط فشل `EADDRNOTAVAIL` | HOSTNAME لا يساوي 0.0.0.0 | تأكد `HOSTNAME=0.0.0.0` في `.env.production` (السكربت يعالجها تلقائياً أيضاً) |
| `bunx prisma` يحاول التنزيل من الشبكة | طبقة أدوات prisma مفقودة من الصورة (تغيير إصدار Prisma) | أعد بناء الصورة كاملة `docker compose build --no-cache app` بعد التأكد من `prisma generate` في builder |
| فشل `bun install --frozen-lockfile` (بناء/CI) | bun.lock غير متزامن مع package.json | حدّث الاعتمادية محلياً بـ `bun install` والتزم bun.lock مع التعديل |
| القاعدة تالفة بعد انقطاع كهرباء | إيقاف غير نظيف (لا init) | تأكد `init: true` في compose (موجودة)؛ ثم استرجع آخر نسخة (§4.2) — لهذا النسخ اليومي إلزامي |
| تحديث المخطط فشل `P1003` / جدول مفقود | نسيت `prisma db push` بعد تحديث schema | نفّذ أمر §3.1 (بعد نسخة احتياطية) |
| حجم القرص ينمو | سجلات Docker + صور قديمة | `docker system prune -f` + مراقبة حجم backups (الدوران آلي) |

## 8.3 إصلاح ملكية وحدة التخزين (نادر)

إن أُنشئ `app-db` بملكية خاطئة (مثلاً بعد تجارب يدوية):

```bash
docker compose exec app sh -c 'ls -ln /app/db'   # لاحظ uid:gid
docker compose stop app
sudo ls -ln /var/lib/docker/volumes/south-wallet_app-db/_data
sudo chown -R 999:999 /var/lib/docker/volumes/south-wallet_app-db/_data   # 999 = uid مستخدم bun داخل الصورة (تحقق منه بالأمر الأول)
docker compose start app
```

## 8.4 إعادة النشر من الصفر (خسارة الشهادة فقط)

آخر ملجأ — بلا مساس بالبيانات:

```bash
docker compose down          # بلا -v أبداً!
docker compose up -d --build
```

# 10. حدود النطاق — ما الذي يظل خارج هذه الحزمة

هذه الحزمة تجعل التطبيق **قابلاً للتشغيل الإنتاجي فعلياً** على خادم واحد (Closed Beta)، وتبقى العناصر التالية خارج نطاقها (تُدار في docs/PRODUCTION_READINESS.md المُعدّ بالتوازي):

| البند | الوضع الحالي | المسار |
|---|---|---|
| مزود SMS حقيقي (OTP) | قناة تجريبية — الرمز يظهر في الإشعار/السجلات | تكامل مزود يمني/إقليمي + متغيرات في `.env.production` |
| مزودو KYC حقيقيون | رفع مستندات داخلي وقرار إداري يدوي | تكامل مزود KYC خارجي |
| مزودو فواتير/شحن حقيقيون | مستحق محاكى حتمي + كروت مولّدة | عقود وتكامل مزودين (A-03) بتمويل FX/Suspense الموجود |
| اختبار اختراق خارجي (PenTest) | مراجعة داخلية فقط | اختبار خارجي قبل الإطلاق العام (RK-07) |
| حسابات التجار الحقيقية (onboarding رسمي) | تاجران تجريبيان بالبذور | مسار تعاقد وKYC تجاري |
| PostgreSQL للنشاط الجماهيري | SQLite مفردة (كافية للـClosed Beta) | خطة ترحيل موثقة في DATABASE_ERD (البنية نفسها على PostgreSQL) |
| تعدد الخوادم / التوسع الأفقي | خادم واحد | بعد تجاوز NFR ومؤشرات النمو |
| التنبيهات المالية القانونية والامتثال البنكي | خارج المستودع تماماً | إجراءات تنظيمية قبل Beta العام |

> **قاعدة الختام**: هذه الحزمة تعطيك «إنتاجاً صغيراً صحيحاً» — قاعدة بيانات محفوظة، نسخ احتياطي مُختبَر، شهادة متجددة، مراقبة، وتراجع. كل توسّع لاحق يُبنى فوقها لا بدلها.
