# 1. المقدمة

## 1.1 الغرض

تحدد هذه الوثيقة المتطلبات الوظيفية وغير الوظيفية لمنظومة **محفظة الجنوب** — محفظة مالية رقمية تعمل على Android وiOS ضمن نطاق جغرافي محدد في جنوب اليمن. وهي المرجع التعاقدي والتقني لـ:

- صاحب المنتج — لاعتماد نطاق العمل والموافقة على المعايير.
- فريق الهندسة — لتصميم المعمارية وقاعدة البيانات وواجهات البرمجة.
- فرق الجودة والاختبار — لبناء حالات الاختبار والقبول.
- فريق الامتثال والمخاطر — لمراجعة ضوابط KYC/AML/CFT.

## 1.2 نطاق المنتج

**محفظة الجنوب** منظومة مالية رقمية متكاملة تقدّم للمستخدم المؤهَّل داخل نطاق الخدمة:

- محفظة متعددة العملات (YER / SAR / USD).
- التحويل الفوري بين مشتركي المحفظة، والتحويل بين محافظ المستخدم نفسه.
- حوالات مالية إلى غير المشتركين واستلامها عبر شبكة وكلاء ونقاط خدمة معتمدة.
- الدفع عبر QR Code أو رقم نقطة البيع لدى التجار.
- سداد الفواتير وشحن رصيد الجوال لجميع الشبكات المحلية.
- السحب والإيداع النقدي عبر الوكلاء.
- صندوق توفير ذكي (الحصالة)، كروت الشبكة، كشف حساب مفصل، إشعارات فورية، مفضلون، ودعم متكامل.

يقدّم النظام أيضاً **لوحة تحكم إدارية** لإدارة المستخدمين والتوثيق والوكلاء والتجار والرسوم والحدود والتسويات ومكافحة الاحتيال والتقارير وسجل التدقيق.

**خارج النطاق (Out of Scope):**
- الإقراض أو التمويل الصغير أو أي منتج ائتماني.
- التداول في العملات الرقمية كخدمة أساسية (مؤجل لمرحلة ما بعد الإطلاق، ومشروط بطبقة Custody مستقلة).
- أي عملية مصرفية تتطلب ترخيصاً مصرفياً كاملاً ما لم يُستوفَ نظامياً.

## 1.3 نظرة عامة على المنظومة

```
        ┌─────────────────────┐
        │   تطبيق Flutter     │  ← عميل / وكيل / تاجر
        │  Android + iOS      │
        └─────────┬───────────┘
                  │ HTTPS / TLS 1.2+
        ┌─────────▼───────────┐
        │    Backend API      │  Authentication → Authorization →
        │  (Node.js/NestJS)   │  Eligibility → Risk → Limits →
        │                     │  Transaction Engine → Ledger
        └───┬──────┬──────┬───┘
            │      │      │
   ┌────────▼┐ ┌──▼───┐ ┌▼─────────────┐
   │PostgreSQL│ │Redis │ │ مزودون خارجيون │
   │ + Ledger │ │Cache │ │ SMS / FCM /   │
   └──────────┘ └──────┘ │ شحن / فواتير / │
                          │ شبكات صرافة   │
                          └───────────────┘
        ┌─────────────────────┐
        │  لوحة تحكم ويب (RTL) │  ← الإدارة بكل أدوارها
        └─────────────────────┘
```

**المبدأ التأسيسي:** قاعدة الحقيقة المالية هي الخادم + دفتر الأستاذ (Ledger)، وليس التطبيق أبداً. التطبيق يعرض الحالة وينقل الطلب ويعرض النتيجة؛ كل قرار مالي يُتخذ ويُسجَّل في الخادم.

| المصطلح | التعريف |

| **MoSCoW** | تصنيف الأولوية: Must / Should / Could / Won't |
| **DoD** | Definition of Done — معيار اكتمال الوظيفة |
| **YER / SAR / USD** | الريال اليمني / الريال السعودي / الدولار الأمريكي |

## 1.6 القواعد الجوهرية غير القابلة للتفاوض

مستمدة من Master PLAN.md وتُعد قيوداً حاكمة على كل متطلب في هذه الوثيقة:

| # | القاعدة |
|---|---|
| R-01 | الخادم + Ledger هما مصدر الحقيقة المالية؛ يُمنع جعل التطبيق أو التخزين المحلي مصدراً للرصيد |
| R-02 | يُمنع تنفيذ أي عملية مالية Offline أو خصم الرصيد محلياً |
| R-03 | كل عملية مالية ذرّية (Atomic) وقابلة للتماثل (Idempotent) ومسجّلة في Ledger |
| R-04 | المعاملة المكتملة لا تُعدَّل أبداً؛ التصحيح يكون بـ Reversal/Adjustment موثّق |
| R-05 | لا "زر تعديل رصيد" مباشر للإدارة؛ كل تعديل مالي يمر عبر Adjustment Request + موافقة + Ledger + Audit |

| R-10 | التطبيق يُعد غير موثوق؛ الخادم يعيد التحقق من كل شيء (المبالغ، الرسوم، المستلم، الحدود، الحالة) |
| R-11 | العربية RTL جزء من التصميم من اليوم الأول، وليست إضافة لاحقة |
| R-12 | التطبيق الأصلي Flutter (ليس WebView)؛ الهوية والشعار والأيقونات أصلية خاصة بمحفظة الجنوب |
| R-13 | عدم وصول Push Notification لا يعني فشل العملية؛ الإشعار قناة إبلاغ فقط |
| R-14 | البيانات المالية وسجلات التدقيق لا تُحذف لأي سبب تنظيفي؛ الحذف المنطقي للمحتوى فقط |

# 2. الوصف العام

## 2.1 منظور المنتج

المنتج منظومة متكاملة من أربعة مكونات مترابطة تعمل على مصدر حقيقة واحد:

1. **تطبيق الموبايل (Flutter):** واجهة العميل والوكيل والتاجر — عربي RTL أولاً مع إنجليزية، يعمل بخدمات المصادقة الآمنة والتخزين المحلي غير المالي.
2. **Backend API (Node.js/NestJS):** القلب المالي — المصادقة، الصلاحيات، الأهلية، محرك المخاطر، الحدود، الرسوم، محرك المعاملات، Ledger، التسويات.
3. **قاعدة البيانات (PostgreSQL + Redis):** التخزين المعاملاتي الدائم + الكاش والجلسات.
4. **لوحة التحكم الإدارية (ويب RTL):** إدارة كاملة للمنظومة بسبعة أدوار إدارية مع Audit شامل.

## 2.2 بيئة التشغيل

| المكوّن | البيئة |
|---|---|
| تطبيق Android | Android 8.0 (API 26) فأعلى |
| تطبيق iOS | iOS 14 فأعلى |
| متصفح لوحة التحكم | Chrome / Edge / Safari / Firefox — آخر إصدارين |
| الشبكة | 3G فأعلى (محسّن لشبكات ضعيفة) |
| الخادم | Docker + CI/CD، بيئات Dev / Staging / Production منفصلة |

## 2.3 أدوار المستخدمين

### 2.3.1 أدوار تطبيق الموبايل

| الدور | الوصف | صلاحيات عامة |
|---|---|---|

## 3.2 المتطلبات الوظيفية — النطاق والأهلية

| ID | المتطلب | الأولوية |
|---|---|---|
| FR-GEO-001 | يعمل النظام بنظام جغرافي مركزي (regions / districts / areas / eligibility_policies) قابل للإدارة من لوحة التحكم؛ لا قائمة مناطق ثابتة في كود التطبيق | Must |
| FR-GEO-002 | كل منطقة تملك: المعرّف، الاسم، الرمز، التفعيل، السماح بالتسجيل، السماح بالمعاملات، ملاحظات | Must |
| FR-GEO-003 | يُمنع التسجيل الجديد من خارج نطاق الخدمة مع رسالة واضحة "الخدمة غير متاحة في منطقتك حالياً" | Must |
| FR-GEO-004 | تقييم الأهلية متعدد الإشارات: المنطقة المسجلة + بيانات التوثيق + رقم الهاتف (مقدّم الخدمة/الرمز) + الإشارات الجغرافية + حالة الحساب + سياسة المنطقة + إشارات الأمان | Must |
| FR-GEO-005 | GPS إشارة مساعدة فقط، ولا يُبنى عليه قرار مالي خطير منفرداً | Must |
| FR-GEO-006 | عند محاولة استخدام من خارج النطاق: تقييد العمليات الحساسة أو إيقاف مؤقت مع إشعار للدعم — دون حذف الحساب أو الأموال | Must |
| FR-GEO-007 | كشف التلاعب بالموقع (GPS Spoofing): فحص mock location APIs، تناقض موقع سريع (سرعة انتقال غير منطقية)، وتناقض GPS مع IP وبصمة الجهاز | Must |
| FR-GEO-008 | كشف VPN/Proxy عبر فحص IP (قواعد ASN/البلد) وتسجيله كإشارة مخاطر، مع سياسة قابلة للتهيئة (سماح/مراجعة/منع) | Must |
| FR-GEO-009 | كشف المحاكيات والروت/الجيلبريك كإشارات مخاطر ترفع مستوى الفحص ولا تمنع تلقائياً إلا بسياسة | Should |
| FR-GEO-010 | بصمة الجهاز تُنشأ عند التسجيل وتُقارن عند كل دخول وكل عملية حساسة | Must |
| FR-GEO-011 | الحد من الحسابات الوهمية: ربط رقم هاتف واحد بحساب واحد، فحص تعدد الأجهزة/الحسابات من نفس البصمة/الIP، ووضع علامة مراجعة KYC مشددة | Must |

## 4.4 محرك المعاملات ودفتر الأستاذ (FR-LDG)

**حالات المعاملة (State Machine):**

```
CREATED → VALIDATING → AUTHORIZED → PROCESSING → COMPLETED
أي من الحالات السابقة يمكن أن تنتهي بـ:
FAILED / REJECTED / CANCELLED / EXPIRED
COMPLETED يمكن أن يتبعها REVERSED
وأي عملية تحت مراجعة: UNDER_REVIEW
```

لا انتقالات عشوائية؛ كل انتقال مسموح معرّف ومسجّل في `transaction_status_history`.

| ID | المتطلب | الأولوية |
|---|---|---|
| FR-LDG-001 | كل تغيير فعلي في الأموال يولّد Ledger Entries متوازنة (مدين/دائن) تشمل أطراف العملية وحساب الرسوم | Must |
| FR-LDG-002 | مثال التحويل: مدين محفظة المرسل → دائن محفظة المستلم + دائن حساب الرسوم؛ المجموع صفر دائماً (Double-Entry) | Must |
| FR-LDG-003 | كل عملية مالية ذرّية: تحقق → قفل سجلات → خصم → رسوم → إضافة → Ledger → Commit، أو Rollback كامل | Must |
| FR-LDG-004 | كل طلب عملية حساسة يحمل مفتاح Idempotency فريد؛ نفس المفتاح = نفس النتيجة دون تنفيذ مزدوج | Must |
| FR-LDG-005 | مرجع معاملة فريد بصيغة `SW-YYYYMMDD-XXXXXXXX` للاستخدام في الإيصالات والبحث والدعم والتدقيق | Must |
| FR-LDG-006 | المعاملة تحفظ Snapshot لكل ما يفسّرها: الخدمة، العملة، المبلغ، الرسوم + `fee_rule_id` + `fee_version`، الأطراف، المزود، المرجع الخارجي، الأوقات، الحالة | Must |
| FR-LDG-007 | التصحيح بعمليات Reversal/Adjustment مرتبطة بالمعاملة الأصلية؛ لا UPDATE للمعاملات المكتملة | Must |
| FR-LDG-008 | كل عملية تمر عبر: صلاحيات → أهلية → فحص مخاطر → فحص حدود → تنفيذ → إشعار → إيصال | Must |
| FR-LDG-009 | عند انقطاع الاتصال بعد إرسال الطلب: عند العودة يستعلم التطبيق عن حالة العملية الأصلية نفسها ولا ينشئ طلباً جديداً | Must |
| FR-LDG-010 | وظيفة Reconciliation دورية (Job) تطابق: مجموع Ledger مقابل مجموع أرصدة المحافظ، وأي انحراف يولّد `RECONCILIATION_ALERT` | Must |
| FR-LDG-011 | محرك الرسوم: قواعد مركزية (خدمة، عملة، مستوى مستخدم، منطقة، مدى مبلغ، ثابت/نسبة بحد أدنى/أقصى، فترة سريان) — لا رسوم مدفونة في كود التطبيق | Must |
| FR-LDG-012 | محرك الحدود المركزي: لكل عملية/يوم/أسبوع/شهر + حد رصيد، حسب (المستخدم، مستوى KYC، العملة، الخدمة، المنطقة)، والفحص = الاستخدام الحالي + المطلوب ≤ الحد | Must |
| FR-LDG-013 | محرك المخاطر: قواعد إشارات (جهاز جديد، محاولات PIN فاشلة، سرعة غير طبيعية، شذوذ الموقع، تكرار، حالة حساب مريبة) → النتائج: `ALLOW` / `REVIEW` / `BLOCK` | Must |
| FR-LDG-014 | محرك الخدمات الموحّد: كل خدمة (شحن/فواتير/بطاقات…) معرفة بـ (فئة، مزود، حقول، تسعير، رسوم، حدود، سير عمل، تفعيل) — لا شاشات مستقلة بلا بنية | Must |

# 11. الملاحق

## ملحق أ: خلاصة الآلات الحالة (State Machines)

| الكيان | الحالات |
|---|---|
| الحساب | `PENDING → ACTIVE ⇄ RESTRICTED ⇄ FROZEN → SUSPENDED → CLOSED` |
| KYC | `NOT_STARTED → PENDING → UNDER_REVIEW → APPROVED / REJECTED / EXPIRED / REQUIRES_UPDATE` |
| المعاملة | `CREATED → VALIDATING → AUTHORIZED → PROCESSING → COMPLETED` (+ `FAILED / REJECTED / CANCELLED / EXPIRED / REVERSED / UNDER_REVIEW`) |
| السحب | `CREATED → PENDING → AUTHORIZED → READY_FOR_COLLECTION → COLLECTED → COMPLETED` (+ رفض/انتهاء/إلغاء/عكس) |
| الحوالة | `CREATED → PENDING_DELIVERY → DELIVERED → COMPLETED` (+ `EXPIRED / CANCELLED / REVERSED`) |
| الأهلية | `ELIGIBLE / PENDING_REVIEW / RESTRICTED / OUTSIDE_SERVICE_AREA / BLOCKED` |
| الخدمة | `ON / OFF / MAINTENANCE` |
| النظام | `ACTIVE / MAINTENANCE / READ_ONLY / SERVICE_DEGRADED / BLOCKED` |
| الوكيل | `ACTIVE / SUSPENDED / BLOCKED` |
